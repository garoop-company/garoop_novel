# Garoop Bunko ― リサーチ先行型の執筆ワークフロー

このスキルは、`garoop-bunko` スキルの上位互換。執筆対象が**実在する人物・企業・地域・出来事**で、ユーザーが**ネット情報の収集を含めた取材**を期待している時に使う。

## 起動条件
- 「○○について Web で調べてから小説書いて」
- 「○○社のニュースを集めて、それを元に文庫を書いて」
- 「実在の人物（X さん）の取材小説を一巻追加して」
- 既存シリーズで、新しい一次情報・最近の動きを反映した続編を依頼された時

`garoop-bunko` スキル単体で書ける（既出キャラの続編で、新規事実取材が要らない）場合は、このスキルではなく `garoop-bunko` を使う。

## 三層フロー

### 第一層: リサーチ（書く前に必ず）

1. **WebSearch を並列で打つ**。一回のメッセージで複数の検索を発射する。最低 3〜4 本。
   - 日本語クエリ: `"<会社名>" 設立 事業内容` `"<人物名>" インタビュー` `<会社名> ニュース 最近` などのバリエーション
   - 英語クエリ: 国際報道や Crunchbase 系データベースを拾うため `"<Company> Japan startup"` など
   - 既知の固有名詞（Garoop なら「ガルちゃん」「GaroopTV」「鍛校」など）も別軸で当てる
2. **検索結果を見て、有望な一次ソースを WebFetch で深掘り**。これも並列で 4 本程度まとめて発射する。
   - 公式サイトトップ
   - 公式 note / プレスリリース / ニュース
   - インタビュー記事（business メディア、地方紙）
   - 行政・支援機関の掲載情報（XX県ビジネス支援プラザなど）
   - 代表者の SNS プロフィール（X, LinkedIn）
3. **取れなかったソースは無理に何度も叩かない**。X や有料サイトは 402/timeout が出やすい。**取れたソースだけで構成する**。
4. **WebFetch のプロンプトに「原文の表現を引用しながら」「印象的なフレーズを抽出して」と必ず書く**。要約より原文の言葉が、後で本文に効く。

### 第二層: ノート化（書く前の整理）

執筆前に、得られた事実を**箇条書きの「事実台帳」**として頭か作業メモにまとめる。最低限以下の枠を埋める:

```
■ 会社/人物の基本
  - 設立日 / 生年 / 所在地（具体的な番地まで取れたら使う）
  - 事業内容（サービス名と一行説明）

■ ミッション・哲学
  - 公式に語られているコピー（「○○○○」と原文ママで）
  - 創業者の信念を象徴するフレーズ

■ 具体的な出来事（時系列で 5〜10 個）
  - YYYY/MM/DD: 何が起きた

■ 個人的な側面・趣味・原体験
  - 過去の経歴、学び、家族、趣味、敗北体験

■ 使えそうな比喩・印象語
  - 「失敗は筋肉痛」「令和の出島」など、本文の核になりそうな言葉
```

事実台帳は**小説の地の文を捏造しないための足場**。台帳にない発言を、人物のセリフとして書かない。

### 第三層: 執筆（garoop-bunko の作法に従う）

1. `garoop-bunko` スキル（同リポジトリ `.claude/skills/garoop-bunko/SKILL.md`）の章スキーマと novels.json の作法に**そのまま乗る**。1 巻 8 ページ、各 400〜600 字、companionLines 8 本。
2. 8 ページの設計は、**事実台帳から特に強い 1 つのエピソード**（連続ローンチの五日間、特定のインタビュー、ある転機）を中心軸に置き、その前後に世界観・原体験・余韻を配置する。事実羅列にしない。
3. **実在の人物の発言**:
   - 公開ソースで本人が語っているコピー（例:「教えない。鍛える」）は鍵かっこ付きでそのまま使える。
   - 一次ソースに無い発言を、本人の直接話法（「○○さんは『...』と言った」）にしない。
   - 内面の独白・地の文の解釈は OK だが、「彼はこう感じた」「彼の中では、こうだった」のような**解釈であることが文体的に分かる**書き方にする。
4. **取材した固有名詞は積極的に**: 出島交流会館8F、長崎県ビジネス支援プラザ、創業日の YYYY/MM/DD、サービス名と価格など、具体は信用を生む。ただし**確証がない数字や年月日は書かない**（「およそ五年」「数年前」のように曖昧表現で逃げる）。
5. **書いてはいけない**:
   - 政治的・宗教的・差別的な見解を、本人の発言として
   - 取材で確認できない経歴詐称につながる記述
   - 競合他社・実在の特定個人へのネガティブな描写
   - 取材で得た私的情報（本人が公開していない家族・健康・恋愛など）

## 一次ソース別の使い方メモ（Garoopの例）

| ソース | 取れる情報 | 使い方 |
|---|---|---|
| `garoop.jp` | 会社の最新の言い方、サービス一覧、採用情報、価格 | 本文の固有名詞・コピーの正確な綴りを揃える |
| `garoop.jp/news` | 時系列のローンチ・登壇・提携 | エピソード設計の骨格 |
| `note.com/garoop` | 代表本人の文体・関心領域・信念 | 内面描写の妥当性を担保 |
| `note.com/garoop_company` | 会社視点の対外メッセージ | サービス・哲学コピーの裏取り |
| `nagasaki-bpp.jp` | 行政側から見た客観事実 | 創業日・拠点の追加裏取り |
| `boienci.jp` (Bowers) | 経営者向け露出での自己紹介 | 経歴・過去の職歴 |
| `create.garoop.jp/plan` | GaroopTV の料金プラン詳細 | 価格や年額の正確な数値 |
| X / LinkedIn | 公開プロフィールと固定情報 | 取れない時は無理に取りにいかない |

## 追加章のレジ作業（garoop-bunko と同じ）

1. `src/data/chapters/<id>.json` に章本体を Write
2. `src/data/novels.json` に新エントリを追加（同 seriesKey の末尾、`episodeNumber` を連番）
3. `npm run build` で全静的ページの生成を確認
4. ユーザーに、追加した章へのファイルパスリンク、リサーチで使った主要ソースの URL（マークダウンハイパーリンク）、本文に取り入れた具体的な事実 3〜5 点を、**簡潔に**報告

## 報告フォーマット例

```
追加した巻: [<title>](src/data/chapters/<id>.json)

リサーチで使った主要ソース:
- [garoop.jp](https://www.garoop.jp/)
- [長崎県ビジネス支援プラザ](https://nagasaki-bpp.jp/...)
- [Garoop Note](https://note.com/garoop_company)

本文に織り込んだ事実:
- 設立日 2023/04/17、本社・長崎市出島町2-11 出島交流会館8F
- 「教えない。鍛える」「失敗は筋肉痛」というコピー
- 2024/12/15-19 の五日間連続ローンチ
- 代表のミリオンダウト Joker1位 10回以上の経歴
```

## 何度も叩いて時間を溶かさない

- WebFetch は同一 URL で再試行しない（15 分キャッシュなのでどうせ同じ）。402/タイムアウトが出たソースは捨てる。
- 取れる情報の総量で書く。「あと一個取りたい」と粘って 5 分溶かすより、手元の事実台帳で書き始めた方が早い。
- **書き終わったあとにユーザーから「ここの事実が違う」と指摘が入ったら、その時点で修正する**。最初から完璧を目指さない。
